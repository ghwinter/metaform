# 大型复杂软件是怎么做出来的

一份面向"明天就要动手"的学习报告。案例都来自本机 D:\GitHub 的仓库，数字是数出来的，结构是读出来的；
凡是我没有逐行确认的，我都写明是"从布局推断"。

---

## 0. 先把问题问准

"它们是不是微内核 + 几组运行时"——这个问法本身有一半是错的，错在把软件分成"内核"和"上层"。
真实的大系统几乎都不是这样长出来的，它们长成的是**一个权威数据模型 + 一张注册表 + 一套分阶段调度**：

- 权威数据模型：整个系统只有一份"世界状态"，所有功能读它、改它；
- 注册表：功能不是被"调用"进来的，而是**注册**进来的（插件、系统、pass、service）；
- 分阶段调度：注册进来的东西按阶段执行，阶段之间是显式的同步点。

"微内核"是操作系统语境下的词，强调"内核只做地址空间与 IPC"。放到应用软件里，对应的东西是
"核心只做数据模型与调度，其余全部是插件"。所以更准确的说法是 **hub-and-spoke（轮毂与辐条）**，
而不是 microkernel。

## 1. 三个案例

### 1.1 bevy：ECS 是数据模型，Plugin 是注册表，Schedule 是调度

规模：crates 目录下 63 个 crate。这不是"分层"，这是**按能力切 crate**。

它的骨架只有三件东西：

1. `bevy_ecs`：`World`（实体、组件、资源的容器）+ `System` trait（bevy_ecs/src/system/system.rs:45）。
   一个 System 是一个可调度的函数，参数由类型系统自动注入——**依赖注入不是靠容器，是靠函数签名**。
2. `bevy_app`：`App` 持有 World 与 Schedule；`Plugin` trait（bevy_app/src/plugin.rs:57）只有一个
   `build(&self, app: &mut App)`，插件能做的全部事情就是往 app 里塞系统、资源、子插件。
3. `bevy_render` / `bevy_asset` / `bevy_scene` 等：都是插件 + 若干 System 的集合。

关键设计后果：

- **功能叠加不需要改内核**：加一个 crate，实现 `Plugin`，在 `add_plugins` 里注册；
- **并行来自调度器**：System 之间的数据依赖由参数声明，调度器据此决定能否并行；
- **性能来自数据布局**：组件按类型分列存储（SoA），遍历是连续内存；
- **宏承担胶水**：`#[derive(Component)]`、`#[derive(Resource)]`、`query!` 这类宏把样板代码消掉，
  宏在这里不是语法糖，而是**让"声明"等价于"实现"**的手段。

一句话：bevy 的核心不是引擎，是**一张能被并行调度的函数表**。

### 1.2 zed：GPUI 是"保留模式的 UI 运行时"，crats 是能力边界

规模：crates 目录下 249 个 crate。哪怕是编辑器，它也是按能力切分（gpui / editor / project / collab / …）。

它的核心是 `gpui`：`app.rs`、`element.rs`、`window.rs` 三个文件就说明了模型——

- **实体（Entity）+ 句柄**：UI 组件不是裸指针互指，而是由统一的 App 持有、用句柄引用；
- **元素树（Element）**：布局与绘制分离，元素树每帧重建，状态留在实体里；
- **窗口是运行时实体**：事件循环在窗口层，业务代码不碰线程。

关键设计后果：

- **状态集中在 App，行为分散在实体**：避免"回调地狱"，也避免"全局单例"；
- **每帧重建轻量树，重状态不重建**：这是 UI 框架能同时保持灵活与性能的通用手法；
- **协作（collab）作为独立 crate**：网络协议与 UI 之间靠消息，不靠共享内存。

### 1.3 tikv：组件是 crate，边界是 trait，分布式逻辑在最上层

规模：components 目录下 70 个 crate。它的分层非常接近教科书：

- 底层：`engine_rocks` / `engine_traits`（存储引擎抽象）、`codec`、`keys`；
- 中层：`raftstore`（一致性）、`storage`（事务与 MVCC）、`coprocessor`（下推计算）；
- 上层：`tikv`（服务装配）、`cdc` / `backup`（旁路功能）。

关键设计后果：

- **trait 在层间，结构体在层内**：跨层只暴露 trait（存储引擎、快照、观察者），
  实现细节锁在 crate 内部；
- **功能是旁路插件**：CDC、备份不是改主链路，而是订阅 raft 日志/快照；
- **性能靠批处理与零拷贝**：`batch-system` 单独成 crate，说明"攒批"是架构级决定，不是优化细节。

## 2. 它们共同的五条不变量

1. **一份权威状态。** 三者的世界都只有一个所有者：bevy 的 World、zed 的 App、tikv 的存储引擎。
   任何"第二份真相"都会立刻产生同步 bug。
2. **注册而非调用。** 新功能不改核心，只注册：Plugin、Element、Service、Observer。
3. **阶段化执行。** 有明确的阶段与同步点（Schedule、帧、raft apply），而不是任意时刻任意回调。
4. **句柄而非指针。** 实体 id、`Handle<T>`、快照 id——跨模块引用一律用可校验的句柄，不用裸引用。
5. **宏/派生承担胶水。** 让"声明一个东西"就等于"实现它的注册与访问"，否则注册表会被样板代码淹没。

## 3. 性能与优雅不是对立面，它们来自同一处

- **数据布局**：SoA、arena、`SmallVec`、`bytes` 零拷贝——减少的是**缓存缺失与拷贝**，不是"代码行数"；
- **批处理**：`batch-system`、bevy 的并行调度——把"每次一点"变成"每次一批"；
- **边界消息化**：跨线程/跨 crate 用消息与句柄，避免共享可变状态；
- **惰性**：UI 每帧重建轻量树、资源懒加载——复杂度花在"必须重建的部分"。

这四条的共同点是：**把重复的路径收束成一个器官**（你上一轮的直觉），
但只收束**状态与通道**，计算仍然分散。

## 4. 如果明天你做一个 engine 或 3A 游戏

### 4.1 分层（按依赖方向，不按"重要性"）

```
core/        数据模型：实体、组件、资源、句柄、事件。零依赖，不含策略
runtime/     调度器、阶段、任务图、时间。只依赖 core
platform/    窗口、输入、文件、线程池。只依赖 core
render/ audio/ physics/ script/   能力 crate，依赖 core + platform
game/        具体玩法，依赖上面全部
tools/       编辑器、资源烘焙，与 game 平级但可反向驱动
```

规则：**依赖只能向下**；跨层通信只用消息与句柄；`core` 里不出现 `std::fs`、不出现 `println!`。

### 4.2 核心结构体的形状

- `World`：组件存储 + 资源表 + 实体分配器。**唯一可变状态**；
- `Entity`：`u32` 索引 + 代际（generation），防止悬垂句柄；
- `Handle<T>`：资源句柄，带引用计数或资产 id，不做跨线程裸引用；
- `System`/`Stage`：函数 + 声明的读写集，供调度器判并行；
- `Plugin`：`fn build(&self, app: &mut App)`，只有这一个入口；
- `Event`：跨阶段传递的唯一允许方式。

### 4.3 Trait 放在哪里

- **跨层**：trait 定义在低层 crate（`RenderDevice`、`Storage`），实现留在高层；
- **层内**：能不用 trait 就不用，结构体 + 泛型更利于内联；
- **插件边界**：trait object 允许，但每帧热路径上不要动态分发。

### 4.4 宏的使用纪律

宏只做三件事：**派生注册**（`#[derive(Component)]`）、**声明式查询**（`query!`）、**样板消除**。
宏不承载业务语义，否则调试栈会不可读。

### 4.5 插件化

插件 = 一个 crate + 一个 `build` 入口 + 一份声明的依赖（它需要哪些资源、注册哪些阶段）。
**插件不能直接改别人的状态**，只能通过 World 的公开 API 与事件。

## 5. 常见反模式

| 反模式 | 症状 | 后果 |
|---|---|---|
| 上帝 World | 所有东西塞进一个全局结构 | 无法并行、无法测试 |
| 到处 `Arc<Mutex<>>` | 跨模块共享可变状态 | 锁顺序死锁、缓存行抖动 |
| 回调地狱 | 事件用函数指针层层注册 | 控制流不可读，无法静态分析 |
| 幽灵单例 | `static mut` / `lazy_static` 全局 | 测试互相污染 |
| 过早抽象 | 先写 trait 再想清楚语义 | 抽象与实现双份维护 |
| 记录式日志 | 到处 `println!` | 无法分级、破坏协议通道（MCP 就是例子） |

## 6. 开工前的检查表

1. 权威状态是什么？只有一个吗？
2. 新功能如何注册？需要改核心吗？
3. 阶段有几个？同步点在哪？
4. 跨模块引用用句柄还是引用？悬垂怎么防？
5. 热路径上的数据布局是什么？有没有不必要的拷贝？
6. 日志/指标走哪个统一出口？
7. 依赖方向有机器检查吗？（没有就会腐化）

## 8. 一句话总结

**大系统不是"内核 + 上层"，是"一个权威世界 + 一张注册表 + 一套阶段调度"，其余都是插件；
性能来自数据布局与批处理，优雅来自依赖方向与句柄纪律。**
